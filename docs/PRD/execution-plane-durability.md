# PRD — Execution-plane durability: `RUNNING`-orphan recovery, reconciler calibration, effectively-once for non-idempotent actions

**Source decisions:** ADR-007 (reconciler / watcher HA via `FOR UPDATE SKIP LOCKED`), ADR-008 (SQS message queue), ADR-065 (forbid-concurrency: at most one *executing* run per `Job`), ADR-067/068 (continuation + `Job.state` — the invariants that turn a stuck run into a wedged job), ADR-022 (cancel best-effort), ADR-055 (containment quotas), ADR-013 (action registry). Origin of the reconciler: issue #30. **New ADRs warranted:** one for `RUNNING`-orphan recovery + the DB-side heartbeat lease; one for the per-action idempotency posture / effectively-once policy.

## Problem Statement

The system's source of truth is the `JobRun` row in Postgres; SQS only tracks *message delivery*. These are two independent state machines coupled solely by the worker's `UPDATE`. The queue's own recovery mechanism — visibility-timeout redelivery + DLQ — recovers a **message**, not a **run**. Three gaps live in that decoupling, and one honesty gap lives in what we can promise:

1. **`RUNNING`-orphan wedges the whole job (highest severity).** A worker that hard-crashes (OOM/SIGKILL/host loss) *after* it atomically claims a run (`status='RUNNING'`) but *before* it writes a terminal status leaves the row stuck in `RUNNING`. The redelivered message cannot recover it: the executor's claim only accepts `PENDING`/`QUEUED`/`RETRYING`, so the next worker's claim fails and it **deletes the message** as an assumed duplicate — throwing away the only recovery vehicle. The reconciler has **no sweep for `RUNNING`**. Under the current architecture this is not a stranded single run: `has_executing_run` (`PENDING`/`QUEUED`/`RUNNING`/`RETRYING`) means the job can never materialize its next recurring tick or downstream — **recurrence and chaining stop permanently** — and `Job.state` never settles (the executor's `settle_job` only fires on a real terminal write), so the job stays `active` forever and **leaks the `active_total` quota**, re-introducing the exact lockout ADR-068 fixed. `task.cancel` cannot clear it either (`RUNNING` is deliberately excluded from the cancellable set, ADR-022).

2. **Reconciler Sweep B prematurely executes future-scheduled runs.** The Watcher claims runs up to a 5-minute lookahead and queues them with an SQS `DelaySeconds` so the message becomes visible at `scheduled_at`. A healthy such row sits in `QUEUED` for minutes. Sweep B re-enqueues any `QUEUED` row whose `updated_at` is older than `queued_grace` (90s) — with **no `scheduled_at` check** — so it re-sends a healthy future-scheduled run with `DelaySeconds=0`, executing it **minutes early** (a recurring @hourly job fires ~3.5 min early every cycle). Claim-and-mark prevents a double-run, but the scheduling contract is violated.

3. **Reconciler grace windows are derived from a stale visibility constant.** The grace derivation assumes `VisibilityTimeout(30s)` (the queue default), but the worker overrides visibility to **60s** per receive and the DLQ queue default is also 60s. The real redelivery lifecycle is ~2× the assumed one, so the DLQ grace can fire before SQS has finished its redelivery attempts.

4. **We cannot honestly claim at-least-once end-to-end for `email_send`.** SQS gives at-least-once *delivery*; end-to-end exactly-once for a non-idempotent external side effect is impossible (two-generals). When a worker crashes mid-`RUNNING` we cannot distinguish "crashed before the Gmail send" from "sent, then crashed before the terminal write," so the reconciler cannot safely blind-retry email. Today `email_send` carries no idempotency key and no write-ahead intent, so the only safe recovery is "give up," which silently drops the mail.

## Solution

- A worker that dies mid-run no longer wedges its job: a **DB-side heartbeat lease** lets the reconciler tell a live long-running worker apart from a dead one, and a new reconciler sweep moves the orphaned `RUNNING` row to a known terminal (or, for idempotent actions, safely back to a claimable status) — so recurrence/chaining resume and the quota slot frees.
- The reconciler stops firing on healthy work: Sweep B only re-enqueues rows that are actually **past due** and still `QUEUED`.
- The reconciler's grace windows are recomputed from the **actual** per-receive visibility, so it stays the *last* responder behind SQS's own redelivery + DLQ.
- `email_send` (and any non-idempotent action) becomes **effectively-once**: a run-derived idempotency key + an app-side dedup record + write-ahead intent shrink the double-send window to a single unavoidable instant, and each action declares its idempotency posture so the reconciler knows whether it may retry or must fail-and-alert. The residual window and the chosen policy are documented, not hidden.

## User Stories

1. As a user with a recurring digest, I want it to keep firing every cycle even if a worker crashes mid-run once, so that one infrastructure blip does not silently stop my schedule forever.
2. As a user chaining "A then B then C", I want the chain to resume after a worker crash in the middle, so that a transient crash does not permanently stall my pipeline.
3. As a user, I want a task whose worker died mid-run to end up in a clear terminal state (`failed`) rather than stuck showing `running` forever, so that my task list tells the truth.
4. As a user, I want a crashed run to free the capacity it was holding, so that I am never locked out of creating new tasks because an old run got stuck.
5. As a user who scheduled a task for 3:00pm, I want it to run at 3:00pm and not minutes early, so that "scheduled" means what it says.
6. As a user with an @hourly recurring job, I want each occurrence to fire at the top of the hour, not ~3.5 minutes early, so that downstream timing (reports, notifications) is correct.
7. As a user whose email task's worker crashed, I want the system to avoid sending me a duplicate email, so that a crash never turns one notification into two.
8. As a user, I want the system to prefer "send my email once, tolerate an extremely rare duplicate" over silently dropping it, so that important mail is not lost — unless the task is flagged high-stakes, where I would rather it fail loudly.
9. As the operator, I want orphaned `RUNNING` rows detected and resolved automatically, so that I never have to do manual DB surgery to un-wedge a job.
10. As the operator, I want the `active_total` quota to reflect only truly-resident load, so that crashed runs do not leak slots and re-create the lockout we already fixed.
11. As the operator, I want a `RUNNING` orphan that is resolved to emit an auditable `RunEvent` (and, for a non-idempotent action, an alert), so that I can see how a run went from `RUNNING` to `FAILED` and investigate root causes.
12. As the operator, I want the reconciler to act only after SQS has exhausted its own redelivery, so that the reconciler never fights the queue or double-sends messages.
13. As the operator, I want Sweep B to touch only genuinely stuck (past-due) `QUEUED` rows, so that the reconciler is not silently executing healthy future work early.
14. As an interviewer reviewing the design, I want the team to state the delivery guarantee precisely (at-least-once delivery + idempotent consumer = effectively-once; exactly-once end-to-end is impossible for external side effects), so that the claim is defensible under questioning.
15. As an interviewer, I want the reconciler's necessity framed as "closing the gap the queue's semantics cannot," so that "why not just rely on visibility timeout?" has a clean answer.
16. As a developer/agent, I want the heartbeat to renew a DB-side lease, not only SQS visibility, so that orphan detection can distinguish a slow-but-alive worker from a dead one regardless of action duration.
17. As a developer/agent, I want the `RUNNING` sweep to reset the row to a claimable status before any re-enqueue, so that a re-sent message is not immediately rejected by claim-and-mark and re-orphaned.
18. As a developer/agent, I want each action to declare `idempotent: true|false`, so that the reconciler's recovery policy (retry vs fail-and-alert) is data-driven, not hardcoded per action.
19. As a developer/agent, I want `email_send` to carry a run-derived idempotency key and an app-side dedup record, so that a redelivered or reconciler-retried send is a no-op at our boundary.
20. As a developer/agent, I want the reconciler grace windows recomputed from the real visibility timeout and expressed via settings, so that a future change to visibility does not silently break the "reconciler is last responder" invariant.
21. As a developer/agent, I want the `CODING_STANDARDS.md` Watcher/Worker rules updated in the same branch as the code, so that review enforces the real claim set and the new lease/orphan rules rather than the stale ones.
22. As a developer/agent, I want new integration tests that drive the real reconciler and executor seams (no faked seams, anti-pattern #10), so that green means the orphan is actually recovered.

## Implementation Decisions

- **DB-side heartbeat lease.** Add a `heartbeat_at` column to `job_runs`. The executor's heartbeat loop, which today only calls `ChangeMessageVisibility`, also bumps `heartbeat_at` on each tick (same cadence, ~30s). The claim sets `heartbeat_at = now` at `RUNNING` transition. This is the signal that separates "alive, still working" from "dead," independent of the action's own timeout.
- **Reconciler Sweep C — `RUNNING` orphan recovery.** New sweep: `status='RUNNING' AND heartbeat_at < now - running_grace` under `FOR UPDATE SKIP LOCKED` (same multi-instance safety as Sweeps A/B). `running_grace` is a small multiple of the heartbeat interval (default ~3× ≈ 90s), and MUST exceed `heartbeat_interval + visibility` slack so a live worker is never swept. Recovery policy is keyed on the action's idempotency posture (below): non-idempotent → `FAILED` + `RunEvent(FAILED, reason='running_orphan')` + operator alert; idempotent → reset to a **claimable** status (`QUEUED`/`RETRYING`) and re-enqueue. Terminal recovery settles `Job.state` and frees the quota by the existing paths (a terminal `RunEvent` flows to the continuation consumer / settle).
- **Sweep B `scheduled_at` guard.** Sweep B's predicate gains `AND scheduled_at < now` (or `scheduled_at <= now`): re-enqueue only rows that are actually due and still `QUEUED`. A future-scheduled row that is healthily waiting on its `DelaySeconds` is left alone.
- **Grace-window recompute.** Re-derive `reconciler_dlq_grace_seconds` and `reconciler_queued_grace_seconds` from the **actual** per-receive visibility (60s), not the queue default (30s), and correct the derivation comments. Add `reconciler_running_grace_seconds`. Keep all three in `app.config.settings` (single source of truth, ADR-010). Also make the reconciler loop `interval` settings-driven (today it is hardcoded).
- **Per-action idempotency posture.** Each `ActionHandler` declares an idempotency posture (e.g. `idempotent: ClassVar[bool]` or an enum). `echo`/`llm_*` (pure/output-only) are idempotent; `email_send`/`slack_post`/`github_digest` (external side effects) are not. The reconciler's `RUNNING` recovery and any future auto-retry consult this flag.
- **`email_send` effectively-once.** Give each logical send a stable idempotency key derived from `run_id`. Before dispatch, write a durable **intent** record (key + "attempting"); after a confirmed send, mark "sent" + store the provider message id. On any replay (SQS redelivery or reconciler retry), the handler checks the dedup record and no-ops if already sent. Document the one residual window ("sent, then crashed before the record write") and the policy: **email biases to at-least-once and tolerates an extremely rare duplicate**; a high-stakes flag flips it to at-most-once + alert.
- **Claim set is unchanged and canonical.** The executor claim stays `WHERE status IN ('PENDING','QUEUED','RETRYING')`; Sweep C's reset-before-re-enqueue exists precisely because a redelivered message cannot claim a `RUNNING` row.
- **Reconciler stays the last responder.** No change to the coordination model: grace windows keep the reconciler behind SQS's redelivery + DLQ, and claim-and-mark remains the arbiter when a sweep and a redelivery overlap (whoever wins the atomic conditional `UPDATE` wins; the other backs off). This PRD only recalibrates the windows and adds the missing sweep.
- **Docs deliverable (same branch as code).** Update `CODING_STANDARDS.md` Watcher/Worker section (already corrected in this branch: real claim set incl. `RETRYING`; the `RUNNING`-orphan known gap becomes an implemented rule once Sweep C lands, plus the heartbeat-lease and grace-calibration rules). Add the new ADR(s). Keep `CONTEXT.md` §2 status machine accurate (no new status values; `RUNNING` unchanged).

## Testing Decisions

A good test asserts **external behavior at the highest existing seam**, drives the **real** path (no faked seams — anti-pattern #10), and uses the real Postgres + ElasticMQ from the compose stack with a fresh engine per test.

- **Reconciler sweeps** — `tests/integration/test_reconciler.py` (existing seam: `reconcile_once()` with injectable grace). Add: a `RUNNING` row with stale `heartbeat_at` past `running_grace` → recovered (non-idempotent → `FAILED` + `RunEvent(reason='running_orphan')` + `Job.state` freed; idempotent → reset-to-claimable + re-enqueued); a `RUNNING` row with **fresh** `heartbeat_at` → untouched (no false positive on a live long-running worker); a `QUEUED` row with old `updated_at` but **future** `scheduled_at` → **not** re-enqueued (Sweep B guard); a past-due `QUEUED` row → still re-enqueued. Mirror the existing "no false positives" test (Test C) for the new cases.
- **Heartbeat lease** — `tests/integration/test_executor.py` (existing seam: `process_one()`): a long action's heartbeat advances `heartbeat_at`; claim sets it at `RUNNING`. Assert the row's `heartbeat_at` moves — the observable that Sweep C keys on.
- **Wedge/unwedge end-to-end** — integration across executor + reconciler + continuation: a job whose only executing run is a stale `RUNNING` orphan is unblocked after Sweep C (a subsequent recurring successor / downstream can now be materialized; `has_executing_run` returns false). Prior art: `test_recurring_watcher.py`, `test_reconciler.py`.
- **`email_send` idempotency** — action-handler seam (unit for the dedup decision, integration for the store): a second dispatch with the same `run_id` idempotency key is a no-op (no duplicate send); intent-then-sent transitions are recorded. Prior art: `tests/unit/test_actions.py`, existing action integration tests.
- **Grace derivation** — assert the settings values match the documented derivation from 60s visibility (guards against the 30s/60s drift returning).

## Out of Scope

- A **forceful "terminate in-flight run"** operation. Cancel stays best-effort/graceful (ADR-022); Sweep C recovers only *dead*-worker orphans (stale lease), never a live `RUNNING` run.
- **Provider-side email dedup** (e.g. switching to a transactional-email API with a native idempotency key). We implement app-side dedup + document the residual window; a provider swap is a separate design.
- **Fan-in** and any change to the run-source model (ADR-040 / ADR-065) — untouched.
- **Replacing SQS with a Postgres-backed queue** (which would collapse the two state machines and remove this whole class of gap) — named as an interview-defensible simplification but a separate, larger effort.
- **Exactly-once end-to-end for external side effects** — impossible in principle; explicitly not promised. The deliverable is *effectively-once* + a documented, bounded residual window.

## Further Notes

- Severity ordering for slicing: (1) `RUNNING`-orphan recovery is highest — it violates the ADR-065 forbid-concurrency guarantee (wedged job) and the ADR-068 quota guarantee (leaked slot). (2) Sweep B guard and (3) grace recompute are small, independent correctness fixes. (4) `email_send` effectively-once is the largest and can land last (Sweep C's non-idempotent path already fails-safe without it).
- The heartbeat-lease decision exists because today's heartbeat renews only SQS visibility; `updated_at` is frozen at claim time, so a `RUNNING` sweep keyed on `updated_at`/`start_at` age would kill legitimately long-running actions. `heartbeat_at` is the fix.
- This PRD closes the gap the reference design (`design-chatgpt-tasks.pdf`) hand-waves as "jobs must be idempotent": our non-idempotent actions (email) force mutual exclusion (claim-and-mark), which neutralizes visibility-timeout redelivery on a hard crash, which is exactly what the reconciler must clean up. Framed for interview defensibility.
